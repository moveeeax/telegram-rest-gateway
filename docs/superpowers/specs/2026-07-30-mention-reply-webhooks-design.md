# Дизайн: вебхуки на упоминание/ответ владельцу аккаунта

Дата: 2026-07-30
Статус: утверждён к реализации
Компонент: telegram-rest-gateway (C++ ядро, Drogon, TDLib)

## Цель

Когда во входящем сообщении явно затронут владелец аккаунта — упоминание или
ответ на его сообщение (а в личке — любое входящее) — доставить полный контекст
сообщения (и, для ответа, всю цепочку reply) на зарегистрированные HTTP-вебхуки.

Основной потребитель — **AI-ассистент/автоответчик**: система на приёмной стороне
читает контекст и формирует ответ/действие, вызывая gateway обратно (agent-токеном).
Отсюда приоритеты: полный контекст и низкая задержка; доставка best-effort (без
строгого at-least-once), но с дедупом повторов на стороне приёмника.

## Триггеры и охват

На каждый `updateNewMessage` выполняется быстрая детекция. `owner_id` — id
собственного аккаунта (из `getMe`), резолвится один раз при авторизации и кэшируется
на время жизни сессии.

Сообщение считается триггером, если оно **входящее** (`message.is_outgoing == false`
и отправитель ≠ владелец) И выполняется хотя бы одно условие:

1. **DM** — тип чата `chatTypePrivate`: любое входящее сообщение (в личке всё
   адресовано владельцу). `trigger_reason = "dm"`.
2. **Нативное упоминание** — `message.contains_unread_mention == true`. В супергруппах
   этот флаг Telegram объединяет @username, mention-по-имени (tap по имени без ника)
   и reply-на-сообщение-владельца. `trigger_reason = "mention"`.
3. **Ответ на сообщение владельца** — у сообщения есть `reply_to`
   (`messageReplyToMessage`), и целевое сообщение отправлено владельцем. Автора
   целевого сообщения `reply_to` напрямую не даёт — он определяется дорезолвом (см.
   «Контекст»). Эта ветка ловит reply в личке и basic-группах, где нативный флаг
   молчит. `trigger_reason = "reply"`.

Приоритет reason при нескольких совпадениях: `mention` > `reply` > `dm`.

**Вне охвата:** каналы-броадкасты (`chatTypeSupergroup` с `is_channel == true`) —
владелец там не собеседник. Исходящие сообщения. Сообщения самого владельца.

**Подтверждённые решения:**
- Входящие **от ботов** — триггерят (не фильтруем по `sender.is_bot`).
- Медиа-сообщения **без текста** — триггерят (фото/видео/голос/документ и т.п.).

## Контекст сообщения и reply-цепочка

Текущий `dto::toJson(const api::message&)` отдаёт только
`id/chat_id/date/is_outgoing/content/reactions` — этого мало для ассистента. Вводится
расширенная проекция (существующая `toJson` не ломается — расширенная либо отдельная
функция, либо надстройка).

Проекция одного сообщения (`webhookMessageToJson`):
```
{
  "id": "...",
  "chat": { "id": "...", "type": "private|group|supergroup", "title": "..." },
  "sender": { "id": "...", "name": "...", "username": "...", "is_bot": false },
  "date": 1730000000,
  "text": "...",                    // текст или caption
  "entities": [ { "type": "mention|mention_name|...", "offset": N, "length": M,
                  "user_id": "..." } ],   // сущности форматирования/упоминаний
  "reply_to_message_id": "...",     // если есть
  "attachment": {                   // если есть вложение
    "type": "photo|video|voice|audio|document|...",
    "file_id": "...", "mime": "...", "size": N, "duration": N, "caption": "..."
  }
}
```
Вложения — **только метаданные + file_id**; содержимое приёмник качает сам через
`GET /v1/files/{file_id}`. Тела в payload не встраиваются.

Конверт вебхук-события:
```
{
  "event_id": "<session_id>:<chat_id>:<message_id>",   // стабильный, для дедупа
  "session_id": "...",
  "owner_id": "...",
  "trigger_reason": "dm|mention|reply",
  "received_at": 1730000000,
  "message": { ...webhookMessageToJson... },
  "reply_chain": [ ...webhookMessageToJson... ],  // всегда при наличии reply_to (любой reason); от родителя к корню; иначе []
  "chain_truncated": false
}
```

**Reply-цепочка** собирается асинхронно подъёмом по `reply_to` через `getMessage`,
начиная с прямого родителя, до корня ветки. Лимит — **20** звеньев; при достижении
лимита или недоступности звена (удалено/нет доступа) сбор останавливается и
`chain_truncated = true`. Порядок в массиве: от прямого родителя к корню.

**Ключевая оптимизация:** первый шаг резолва цепочки одновременно (а) проверяет
условие триггера reply (автор родителя == владелец) и (б) даёт первое звено цепочки.
Один проход getMessage, без дублирующих запросов.

## Регистрация вебхуков (REST + S3)

Динамическая регистрация в рантайме, персистентность отдельным файлом в S3
(тем же механизмом, что сессия). Файл — **per session**: `webhooks.json` по ключу
рядом с объектом сессии данной сессии.

Эндпоинты (scope `admin`, за bearer-фильтром):
- `POST /v1/webhooks` — тело `{ "url": "...", "secret": "...", "active": true }`;
  ответ `{ "id": "<uuid>", "url": "...", "active": true }`. `secret` в ответе и в
  GET не отдаётся (write-only).
- `GET /v1/webhooks` — список зарегистрированных (без `secret`).
- `DELETE /v1/webhooks/{id}` — удалить.

Хранилище:
- При старте: загрузить `webhooks.json` из S3 в in-memory реестр. Файла нет / S3
  недоступен → пустой реестр + WARN (не падать).
- При каждом изменении (POST/DELETE): обновить in-memory и сохранить в S3. Ошибка
  сохранения → ERROR + метрика; in-memory остаётся источником истины до перезапуска.
- Под на сессию один (`replicas: 1`, `Recreate`) — конкурентной записи файла нет.

## Доставка

Доставка выполняется на **выделенном воркер-пуле**, вне потока-приёмника TDLib и вне
IO-петель Drogon (тот же принцип изоляции, что у `KafkaSink`). Поток-приёмник только
кладёт готовый payload в очередь диспетчера и не блокируется.

На событие: POST на **все `active`** вебхуки реестра. Модель — **одна попытка,
fire-and-forget**:
- Таймаут на попытку ~10 c (конфигурируемый).
- При сетевом сбое / не-2xx — `drop`, инкремент метрики `tgw_webhook_failed_total`,
  WARN. Ретраев нет.
- Успех — `tgw_webhook_delivered_total`.
- Переполнение очереди диспетчера → `drop` + `tgw_webhook_dropped_total` (backpressure,
  как у Kafka-очереди).

Аутентификация вызова к приёмнику:
- Заголовок `X-TGW-Signature: sha256=<hex hmac_sha256(secret, raw_body)>`.
- Заголовки `X-TGW-Event-Id`, `X-TGW-Session-Id`, `Content-Type: application/json`.
- `event_id` стабилен (`session:chat:message`) — приёмник дедуплицирует повторные
  доставки одного сообщения (возможны при реконнекте TDLib).

SSRF: URL задаёт оператор через admin-API (доверенный ввод), поэтому риск ниже, чем у
пользовательского `/backfill` архиватора. Тем не менее добавляется опциональный
allowlist/дени приватных диапазонов (флаг конфига, по умолчанию выкл. — как компромисс
доверенного оператора), чтобы не регрессировать урок archiver-SSRF при будущем
переиспользовании.

## Компоненты (изоляция и тестируемость)

- **`OwnerMentionDetector`** (заголовок, чистые функции) — `detect(const api::message&,
  std::int64_t owner_id, ChatKind) → std::optional<TriggerReason>`. Возвращает `dm` /
  `mention` сразу; при наличии `reply_to` без иных совпадений возвращает маркер
  `reply_pending` (нужен async-резолв автора родителя). Без сети — юнит-тестируема.
- **`ContextBuilder`** (async, поверх `TdBridge`) — строит расширенную проекцию
  сообщения и reply-цепочку через `getMessage`; заодно закрывает проверку
  reply-владельца. Тест на `FakeTdTransport`: обрыв цепочки, достижение лимита,
  родитель-владелец vs чужой родитель.
- **`WebhookRegistry`** — in-memory набор + сериализация в/из S3. Тест на фейковом
  S3-слое (по образцу `session_io`/`s3_session` тестов): load пустого/непустого,
  save, отсутствие файла.
- **`WebhookDispatcher`** — воркер-пул, формирование запроса, HMAC-подпись, таймаут,
  метрики, backpressure. Тест на мок-HTTP-приёмнике: корректность подписи, заголовков,
  поведение при таймауте/не-2xx, доставка нескольким вебхукам.
- **REST-роуты `/v1/webhooks`** — регистрация/список/удаление; проверка scope admin.
  Покрытие через route-smoke (bearer-фильтр на путях) + юнит на парсинг тела.
- **Интеграция в `UpdateRouter::onUpdate`** — на `updateNewMessage`: детект →
  (если триггер) запустить async `ContextBuilder` → передать payload в
  `WebhookDispatcher`. Не блокирует поток-приёмник; async-задача резолвит цепочку и
  диспетчеризует.

## Поток данных

```
updateNewMessage (поток-приёмник TDLib)
  → OwnerMentionDetector.detect(...)
      • dm / mention          → триггер сразу
      • reply_pending         → требуется async-проверка родителя
      • nullopt               → выход (не наш случай)
  → async-задача (не блокирует приёмник):
      ContextBuilder:
        • построить проекцию текущего сообщения
        • если reply_pending (не было mention/dm): getMessage(родитель) →
              автор == owner?  нет → не триггер, выход
                               да  → триггер reason=reply
        • если у сообщения есть reply_to (при ЛЮБОМ reason): собрать reply_chain —
              подниматься по reply_to до корня (лимит 20); первый getMessage
              переиспользуется как проверка выше и как звено 1 (без дубля запроса)
        • собрать конверт события (event_id, reason, message, reply_chain, ...)
      → WebhookDispatcher.dispatch(event)
  → WebhookDispatcher (воркер-пул):
      для каждого active вебхука: POST url, HMAC-подпись, таймаут, метрика
```

## Обработка ошибок

- `getMe`/owner_id недоступен на момент апдейта → пропустить детекцию reply/ mention
  до готовности owner_id (кэш заполняется при Ready); DM-триггер по типу чата не
  требует owner_id.
- `getMessage` при сборе цепочки фейлит → остановить сбор, `chain_truncated = true`,
  доставить с частичной цепочкой.
- Вебхук недоступен/не-2xx/таймаут → drop + метрика, без ретраев.
- S3 `webhooks.json`: недоступен при старте → пустой реестр + WARN; ошибка save →
  ERROR + метрика, in-memory не теряется.
- Диспетчер перегружен → drop + метрика (backpressure).
- Все async-операции — вне потока-приёмника TDLib и IO-петель Drogon.

## Тестирование

- Юнит: `OwnerMentionDetector` (dm/mention/reply_pending/none; исходящие; каналы;
  боты триггерят; медиа-без-текста триггерит).
- Юнит на `FakeTdTransport`: `ContextBuilder` — цепочка до корня, лимит 20 →
  truncated, обрыв на недоступном звене, reply-владелец vs чужой.
- Юнит: `WebhookRegistry` S3 load/save (фейк-S3).
- Юнит: `WebhookDispatcher` — HMAC-подпись (известный вектор), заголовки, таймаут,
  не-2xx → failed-метрика, доставка нескольким.
- Route-smoke: `/v1/webhooks` за bearer-фильтром (admin), health/ready не задеты.
- Все новые тесты — зелёные под ASan/TSan (диспетчер и реестр — кросс-поточные).

## Конфигурация (env / helm)

- `TGW_WEBHOOKS_ENABLED` (bool, default false) — мастер-выключатель фичи.
- `TGW_WEBHOOK_TIMEOUT_MS` (default 10000) — таймаут попытки доставки.
- `TGW_WEBHOOK_QUEUE_MAX` (default напр. 10000) — предел очереди диспетчера.
- `TGW_WEBHOOK_SSRF_GUARD` (bool, default false) — запрет приватных диапазонов в URL.
- Ключ S3 для `webhooks.json` — производный от текущего ключа сессии (per session).
- Все новые переменные документируются в README и helm values.

## Вне скоупа (YAGNI)

- Ретраи/персистентная очередь доставки (выбрана fire-and-forget).
- Встраивание содержимого вложений (только file_id).
- Фильтры подписки per-webhook (по чатам/типам триггеров) — в v1 все триггеры идут
  всем active вебхукам; фильтры можно добавить позже без слома контракта.
- Дедуп на стороне gateway (дедуп — ответственность приёмника по `event_id`).
