# Дизайн: имитация человеческой печати перед отправкой сообщения

Дата: 2026-07-30
Статус: утверждён к реализации
Компонент: telegram-rest-gateway (C++ ядро, Drogon, TDLib)

## Цель

При отправке текстового сообщения через `POST /v1/chats/{chatId}/messages`
имитировать поведение живого человека: показать собеседнику индикатор
«печатает…», выдержать паузу, пропорциональную длине сообщения (со случайным
разбросом), и только затем отправить сообщение. Основной потребитель —
AI-ассистент/автоответчик (та же аудитория, что у фичи вебхуков): мгновенный
ответ бота выглядит неестественно, пауза делает автоответ неотличимым от
живой переписки.

## Область действия

Только `POST /v1/chats/{chatId}/messages` (текстовые сообщения).
Редактирование (`PATCH .../messages/{messageId}`), пересылка
(`.../messages/forward`) и загрузка файлов (`.../files`) не затрагиваются —
сознательно вне скоупа (YAGNI, можно добавить позже без слома контракта).

Включается глобально флагом `TGW_HUMANIZE_TYPING` (bool, default `false`).
При выключенном флаге поведение эндпоинта не меняется вообще.

Пауза применяется только к реальной попытке отправки: если запрос отклонён
валидацией (пустой/отсутствующий `text`, битый `chat_id`, ошибка
`parse_mode`) или отдан из `IdempotencyCache` как повтор (`Idempotency-Key`
уже закэширован/в полёте) — эти пути завершаются как сегодня, без паузы и
без индикатора «печатает…» (пауза не имеет смысла, когда реальной отправки
не происходит).

## Формула паузы

Чистая функция (тестируемая без сети и без TDLib):

```
base_ms    = len(text_utf8_chars) / (chars_per_minute / 60000)
jittered   = base_ms * uniform(1 − jitter, 1 + jitter)
delay_ms   = clamp(jittered, min_delay_ms, max_delay_ms)
```

Источник случайности передаётся параметром (не берётся из глобального RNG) —
тесты детерминированы, подавая фиксированное значение вместо честного
`uniform()`.

Конфигурация:
- `TGW_HUMANIZE_CHARS_PER_MINUTE` (int, default `200`)
- `TGW_HUMANIZE_JITTER_PERCENT` (int, default `20`)
- `TGW_HUMANIZE_MIN_DELAY_MS` (int, default `1000`)
- `TGW_HUMANIZE_MAX_DELAY_MS` (int, default `10000`)

Длина текста считается в UTF-8 кодпоинтах (не байтах) — сверяется с тем, как
остальной код проекта уже считает длину текста сообщений (см. существующие
использования при валидации в `message_routes.cpp`).

## Индикатор «печатает…»

TDLib/Telegram не поддерживают видимость `chatActionTyping` сами — индикатор
у собеседника гаснет без подтверждения через несколько секунд (тот же класс
проблемы, что уже найден и исправлен для `TGW_KEEP_ONLINE`: TDLib не пингует
сервер за клиента). Поэтому на время всей паузы:

- сразу отправляется `sendChatAction(chat_id, chatActionTyping)`;
- затем переотправляется каждые **4 секунды** (константа, не выносится в
  конфиг — короче любого реалистичного порога исчезновения индикатора и не
  требует настройки), пока пауза не истечёт.

`sendChatAction` — fire-and-forget (`bridge.sendOneWay`), не влияет на тайминг
паузы и не участвует в HTTP-ответе.

## Ожидание настоящего id сообщения

TDLib `sendMessage` синхронно возвращает объект сообщения с **временным**
(локальным) id; сервер присваивает окончательный id позже, доставляя его
через апдейт `updateMessageSendSucceeded` с полем `old_message_id_`,
указывающим на тот самый временный id. Текущий код гейтвея не ждёт этот
апдейт — эндпоинт сразу отвечает `202 Accepted` с временным id, финальный id
доступен только тем, кто слушает `/v1/updates` (WS).

Новое поведение: после вызова `sendMessage` и получения временного id
гейтвей **дополнительно ждёт** до `TGW_HUMANIZE_ID_WAIT_MS` (default `4000`)
подтверждающий апдейт для этого temp id.

### Новый компонент: `MessageSendTracker`

По образцу `CorrelationMap` моста (`src/bridge/correlation_map.hpp`) — но
ключ не request_id, а `old_message_id` (int64) сообщения:

- `waitFor(old_message_id, timeout_ms) -> Awaitable<optional<message>>` —
  регистрирует ожидание, приостанавливает корутину, резолвится либо когда
  придёт `resolve(...)` с этим id, либо по истечении `timeout_ms` (аналог
  TTL-sweep в `TdBridge`) — тогда возвращает `nullopt`.
- `resolve(old_message_id, message_or_error)` — вызывается из
  `UpdateRouter::onUpdate` на `updateMessageSendSucceeded`/`Failed`, **в
  дополнение** к существующему WS-форвардингу этого апдейта (форвардинг не
  убирается — другие подписчики `/v1/updates` по-прежнему должны его видеть).
- Мьютекс-защищённая карта, единственный резолвер на запись (как в
  `CorrelationMap` — «резолвит РОВНО ОДНА сторона»), потокобезопасность по
  тому же принципу: запись — из потока-приёмника TDLib, ожидание — из
  корутины HTTP-хендлера (marshalling резюма — тот же паттерн, что у
  `TdAwaitable`).

`updateMessageSendFailed` тоже резолвит ожидание (с ошибкой) — если реальная
отправка провалилась ДО истечения `id_wait_ms`, хендлер должен вернуть
`telegramError`, а не подставной успех.

## Контракт ответа

- **Дождались подтверждения** (`updateMessageSendSucceeded` пришёл до
  таймаута) → `200 OK`, `data` = полная проекция сообщения (тот же формат,
  что `dto::toJson(message)` в `updateNewMessage`), `sending_state: "sent"`.
- **Не дождались** (таймаут `id_wait_ms` истёк) → `202 Accepted`, как сейчас:
  `{"temporary_message_id": ..., "chat_id": ..., "sending_state": "pending"}`.
- **Отправка провалилась** (`updateMessageSendFailed` пришёл до таймаута)
  → `telegramError(...)` с деталями ошибки TDLib (как для любого другого
  провала `sendMessage` сегодня).
- Idempotency-Key кэширует итоговый ответ (какой бы из трёх исходов ни
  случился) — существующая логика `IdempotencyCache` не меняется.

## Бюджет таймаутов инфраструктуры

При включённом `TGW_HUMANIZE_TYPING` худший случай длительности запроса —
`TGW_HUMANIZE_MAX_DELAY_MS + TGW_HUMANIZE_ID_WAIT_MS` (default
`10000 + 4000` = 14 с). Проверено фактическое состояние:

- Drogon `idle_connection_timeout` — нигде не задан явно в коде, используется
  встроенный дефолт **60 секунд** (подтверждено по официальному
  `config.example.yaml`: «lifetime of the connection without read or
  write»).
- Ingress гейтвея (`deploy/helm/telegram-rest-gateway`) — аннотации
  `proxy-read-timeout`/`proxy-send-timeout` сейчас **не заданы вовсе**,
  используется дефолт `nginx-ingress-controller` (подтверждено на живом
  кластере: конфигурация контроллера таких значений не переопределяет) —
  тоже 60 секунд.
- MCP (`telegram_send_message` → `POST /v1/chats/{chatId}/messages`) — общий
  fetch-хелпер `api()` в `mcp/src/index.ts` не задаёт `AbortSignal`/таймаут
  вовсе — со стороны MCP риска нет.

Оба серверных таймаута сейчас совпадают на 60 с случайно (это дефолты
разных систем, не согласованное решение) — с запасом покрывают худший случай
14 с, но полагаться на совпадение дефолтов нельзя.

Действия:
1. Завести `TGW_IDLE_CONNECTION_TIMEOUT_SECONDS` (int, default `90`),
   выставлять явно через `drogon::app().setIdleConnectionTimeout(...)` в
   `main.cpp` (сейчас не вызывается вообще).
2. В `deploy/helm/telegram-rest-gateway` добавить в `values.yaml` дефолтные
   ingress-аннотации `proxy-read-timeout: "90"` / `proxy-send-timeout: "90"`
   (сейчас отсутствуют; MCP-чарт уже задаёт похожие аннотации для своих
   стриминговых нужд — тот же приём, применённый к гейтвею).
3. **Fail-fast guard** при старте (`Config::load` или сразу после): если
   `TGW_HUMANIZE_MAX_DELAY_MS + TGW_HUMANIZE_ID_WAIT_MS` (плюс запас, скажем
   2000 мс на сетевые накладные расходы) `> TGW_IDLE_CONNECTION_TIMEOUT_SECONDS * 1000`
   — процесс отказывается стартовать с понятным сообщением об ошибке (тот же
   принцип, что required `image.tag` в Helm-чарте) — чтобы будущая правка
   одного параметра не тихо ломала другой без видимого симптома до продакшна.

## Тестирование

- Чистая функция расчёта паузы: границы `min/max`, направление `jitter`,
  детерминированность при фиксированном источнике случайности.
- `MessageSendTracker`: на `FakeTdTransport`/скриптованных апдейтах (по
  образцу `ContextBuilder`-тестов) — успешный резолв до таймаута, таймаут без
  апдейта, резолв через `updateMessageSendFailed`, отсутствие двойного
  резолва одного ожидания.
- Fail-fast guard: юнит-тест на `Config::load`/старте — сочетание значений,
  превышающее `idle_connection_timeout`, даёт понятную ошибку, а не тихий
  прод-баг.
- Route-smoke: `/v1/chats/{chatId}/messages` при включённом флаге всё ещё
  требует `write`-scope и не ломает существующий bearer-фильтр.

## Вне скоупа (YAGNI)

- Редактирование/пересылка/файлы — не трогаются.
- Per-request отключение режима (флаг в теле запроса) — обсуждалось,
  отклонено в пользу глобального конфига, консистентного с остальными
  флагами проекта (`TGW_KEEP_ONLINE`, `TGW_WEBHOOKS_ENABLED`).
- Отмена/прерывание паузы при поступлении нового сообщения от собеседника —
  не запрошено, не реализуется.
