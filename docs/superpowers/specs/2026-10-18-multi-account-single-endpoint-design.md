# Дизайн: единая точка входа и многоаккаунтность

Дата: 2026-10-18
Статус: черновик, ждет утверждения владельцем
Компоненты: gateway (C++), mcp (TS), archiver (TS), новый control plane (TS), Helm-чарты, кластер `oci-k3s`, namespace `tgw`

## Зачем

Сейчас каждый Telegram-аккаунт это отдельный набор: под гейтвея со своим хостом `tg-<id>`, под MCP со своим хостом `mcp-<id>`, по сертификату на каждый. Аккаунты перечислены руками в values двух чартов, первый логин идет через `kubectl port-forward` и `/ui`. В claude.ai у владельца висит по коннектору на аккаунт.

Владелец хочет:

1. Один адрес для API и один для MCP. Какой аккаунт обслуживать, определяет токен.
2. Аккаунты не только свои, но и чужих людей.
3. Легкий онбординг нового клиента: открыл ссылку, отсканировал QR в Telegram, получил токен.
4. Архиватор сейчас не в приоритете, но если переделывать, то под новую модель.

Воркер на аккаунт остается: один под держит ровно одну Telegram-сессию. Это решение по итогам анализа, см. раздел «Почему не один процесс на всех».

## Цели

1. Общие хосты `tg.tarassov.me` (REST и WebSocket) и `mcp.tarassov.me` (MCP Streamable HTTP). Старые per-account хосты живут до миграции клиентов, потом удаляются.
2. Токен клиента однозначно определяет аккаунт. Чужой токен на чужой аккаунт не попадает ни при какой подмене пути, заголовка или регистра.
3. Новый аккаунт добавляется без правки values, без `helm upgrade` и без ожидания нового сертификата.
4. Онбординг по одноразовой ссылке: QR основной путь, телефон с кодом и 2FA-паролем запасной. Оператор в процессе не участвует, кроме выдачи приглашения.
5. Один MCP-процесс на всех. Владелец с несколькими аккаунтами может держать один коннектор.
6. Изоляция тенантов: свой токен, свой ключ шифрования БД TDLib, свой срез архива. Тенант не получает admin-скоуп и не может выгрузить session string.
7. Удаление аккаунта: logout в Telegram, остановка воркера, зачистка S3, секретов и архива.

## Не цели

1. Многоклиентный гейтвей (несколько TDLib-клиентов в одном процессе).
2. Самостоятельная регистрация без приглашения.
3. Биллинг, квоты, личный кабинет с историей.
4. Вебхуки для тенантов. Остаются admin-функцией, тенант их не настраивает. Можно добавить позже через control plane.
5. Горизонтальное масштабирование MCP и архиватора больше одной реплики.
6. OAuth для MCP-коннектора.

## Анти-цели

То, что делает работу провалом, даже если все формально работает:

1. Любой путь, по которому тенант А читает или пишет от имени тенанта Б: через API, WebSocket, MCP, поиск по архиву, медиа-ссылки, кэш идемпотентности.
2. Два живых процесса на одну сессию. Это AUTH_KEY_DUPLICATED, сессия сгорает, нужен повторный логин.
3. Тенант получает session string своего или чужого аккаунта или admin-токен.
4. Открытая регистрация, через которую кто угодно заводит аккаунты на общий `API_ID`. Блокировка `API_ID` со стороны Telegram ударит по всем.
5. Потеря логина нового клиента из-за того, что бинлог не успел уехать в S3.

## Срочное, до основной работы (фаза 0)

Найдено при анализе живого кластера 2026-10-18. Делается отдельным изменением, от дизайна не зависит.

1. На пяти Ingress в `tgw` нет IP-allowlist. В кластере Traefik 3.7.13, аннотации `nginx.ingress.kubernetes.io/*` он не читает, так что guard в `_helpers.tpl` проверяет не тот ключ. С постороннего IP без токена отдаются `/ui` и `/metrics` обоих гейтвеев.
2. Задеплоенный чарт старше коммита с guard'ом, следующий `helm upgrade` из HEAD упадет на guard.
3. `telegram_search_history` в MCP не передает `session_id`, архиватор ищет по всем аккаунтам. Коннектор одного аккаунта отдает переписку другого.
4. После логина бинлог уходит в S3 только по таймеру (до 300 с). Нужен push по событию Ready.

Что сделать:

1. Traefik Middleware `ipAllowList` на все пять Ingress. Перед этим проверить, видит ли Traefik реальный IP клиента за OCI LB: включить access log, сделать запрос с известного IP. Если видит IP балансировщика, allowlist бесполезен, и тогда `/ui` и `/metrics` снаружи просто закрыть.
2. `/metrics` убрать из внешних маршрутов.
3. Guard в обоих чартах принимает Traefik-аннотацию `traefik.ingress.kubernetes.io/router.middlewares` наравне с nginx-ключом. `className: nginx` заменить на `traefik`.
4. MCP передает `session_id` своего аккаунта в `/search`.
5. Гейтвей пушит бинлог в S3 сразу после первого `Ready`.
6. DEPLOY.md привести к реальности: кластер `oci-k3s`, Traefik, DNS-01 через Cloudflare, MinIO внутри кластера.

## Архитектура

```
                    tg.tarassov.me                 mcp.tarassov.me          join.tarassov.me
                          │                              │                         │
                    ┌─────┴──────────────── Traefik (IngressRoute) ────────────────┴─────┐
                    │ Authorization / Sec-WebSocket-Protocol      X-API-Key / Bearer     │
                    │ префикс токена <accountId>. → Service       → один MCP              │
                    └─────┬──────────────────────────────┬──────────────────────┬────────┘
                          │                              │                      │
             ┌────────────┴─────────┐          ┌─────────┴────────┐    ┌────────┴────────┐
             │ worker tgw-<acc>     │◄─────────┤ mcp (1 под)      │    │ control plane   │
             │ StatefulSet, 1 под   │  service │ реестр токенов   │    │ инвайты, онборд │
             │ свой Secret          │  token   │ из control plane │    │ reconcile k8s   │
             └──────┬───────────────┘          └─────────┬────────┘    └──┬──────────┬───┘
                    │ Kafka tgw.updates                  │ /search        │ K8s API  │ Postgres
                    ▼                                    ▼                ▼          ▼
               archiver (internal only, session_id обязателен)      Secret/STS/Svc/Route  accounts
```

### Идентификатор аккаунта

1. `accountId` это постоянный идентификатор аккаунта в системе. Он же `TGW_SESSION_ID`, сегмент ключа S3, ключ Kafka, `session_id` в архиве, суффикс имени K8s-ресурсов.
2. Для новых аккаунтов `accountId` это случайный slug: `a` плюс 10 символов `[a-z0-9]`. Telegram user id в имена хостов, ресурсов и логов ingress не попадает.
3. Telegram user id и username хранятся в таблице `accounts` control plane и в `meta.json` рядом с бинлогом в S3 (`telegram-sessions/<accountId>/meta.json`).
4. Два существующих аккаунта сохраняют `accountId` равным их числовому id. Переименование не нужно: числовой id проходит валидацию `isSafeSegment` и годится как DNS-сегмент.
5. Slug выбран, чтобы не делать двухфазного старта: воркер, на котором прошел логин, и есть постоянный воркер аккаунта.

### Токены

Формат клиентского токена: `<accountId>.<secret>`, где `secret` это 32 байта из CSPRNG в base64url. Префикс нужен только для маршрутизации в Traefik. Проверяется токен целиком по SHA-256 в том месте, куда пришел запрос.

| Токен | Кто держит | Где проверяется | Скоупы |
|---|---|---|---|
| Клиентский | тенант | под аккаунта (BEARER_TOKENS) и MCP (реестр) | read,write у гейтвея; все инструменты в MCP |
| Админский аккаунта | только control plane | под аккаунта | read,write,admin |
| Сервисный MCP→гейтвей | MCP, получает из control plane | под аккаунта | read,write |
| Сервисный MCP→архиватор | MCP | архиватор | поиск с `session_id` |
| Сервисный архиватор→гейтвей | архиватор, получает из control plane | под аккаунта | read (скачивание медиа, backfill) |
| Админ control plane | владелец | control plane | инвайты, список и удаление аккаунтов |

Клиентский токен один на API и на MCP: тенанту не надо держать два значения. MCP при этом не передает его в гейтвей, а ходит своим сервисным токеном. Так требует спецификация MCP (запрет token passthrough, раздел security best practices редакции 2025-11-25).

Владельцу control plane может выдать токен на несколько аккаунтов, но только для MCP: формат `owner.<secret>`, в реестре MCP он ссылается на набор `accountId`. Для REST у владельца остаются токены на каждый аккаунт, потому что маршрутизация в Traefik идет по префиксу и набор не поддерживает.

Отзыв и ротация клиентского токена: control plane меняет Secret аккаунта и перезапускает под. Перезапуск безопасен, сессия уезжает в S3 на graceful shutdown. Горячая перезагрузка токенов в гейтвее не делается в этой итерации.

### Маршрутизация (Traefik)

Решение: IngressRoute на аккаунт с матчингом по префиксу токена. Свой роутер не пишем, Traefik уже стоит.

На каждый аккаунт control plane создает один IngressRoute для `tg.tarassov.me`:

1. `HeaderRegexp(Authorization, ^Bearer <accountId>\.)` или `HeaderRegexp(Sec-WebSocket-Protocol, ^bearer\.<accountId>\.)` ведет в Service `tgw-<accountId>`.
2. Маршрута на `/v1/auth/`, `/v1/webhooks`, `/ui`, `/metrics` через общий хост нет. Эти пути открываются только изнутри кластера (control plane) или через старые хосты за allowlist до их удаления.

Регистр. Drogon матчит пути без учета регистра, поэтому блокировку путей в Traefik делать регистронезависимо (`PathRegexp` с `(?i)`), либо проще: на общем хосте пропускать только allowlist префиксов `/v1/chats`, `/v1/me`, `/v1/users`, `/v1/contacts`, `/v1/resolve`, `/v1/search`, `/v1/files`, `/v1/updates`, `/v1/health` без учета регистра, остальное 404. Выбор формы правила за исполнителем, проверка обязательна (см. «Проверка»).

Запрос без токена или с неизвестным префиксом получает 404 от низкоприоритетного правила.

`mcp.tarassov.me` ведет в единственный Service MCP без условий на заголовки. MCP сам разбирает токен.

`join.tarassov.me` ведет в control plane, только пути онбординга (см. ниже).

Сертификат: wildcard не нужен. Хостов теперь фиксированно три (`tg`, `mcp`, `join`), у воркеров собственных хостов нет. Один Certificate с тремя SAN через существующий ClusterIssuer `letsencrypt-prod` (DNS-01 Cloudflare). Новый аккаунт сертификата не ждет. Secret сертификата не должен быть доступен Role control plane: либо отдельный namespace для Traefik-объектов общего хоста, либо Role с `resourceNames` только на Secret аккаунтов (выбор за исполнителем).

### Воркер аккаунта

Шаблон тот же, что сейчас в чарте гейтвея, с изменениями:

1. StatefulSet с `replicas: 1` вместо Deployment. При потере ноды StatefulSet не создает замещающий под, пока старый не удален. Deployment через 300 с toleration создал бы второй под рядом с живым на отрезанной ноде.
2. Свой Secret `tgw-<accountId>`: `BEARER_TOKENS` (клиентский, админский, сервисный MCP), `DATABASE_ENCRYPTION_KEY` (свой на аккаунт). Общий Secret остается только для `API_ID`, `API_HASH`, S3-кредов.
3. `TGW_SESSION_EXPORT_ENABLED=false` для всех воркеров, включая аккаунты владельца. Владелец может включить экспорт на своем аккаунте через admin API (поле `export_enabled` в `accounts`, по умолчанию `false`, для тенантов недоступно). После миграции экспорт на двух существующих аккаунтах выключен, пока владелец его не включит.
4. Requests и limits как сейчас (50m/64Mi, 500m/256Mi). Ориентир масштаба: до 50 аккаунтов. По состоянию кластера на 2026-10-18 (6 нод, CPU 4-8%, память 9-21%) запас есть, точную память TDLib на аккаунт надо замерить на первых тенантах.
5. Лейблы `tgw.tarassov.me/account-id=<accountId>` и `tgw.tarassov.me/managed-by=control-plane`.
6. NetworkPolicy: под принимает трафик только от Traefik, MCP, control plane, архиватора.

Существующие два аккаунта переходят на этот шаблон. Их `DATABASE_ENCRYPTION_KEY` переносится в их собственные Secret без изменения значения, иначе бинлоги в S3 не расшифруются.

### Онбординг нового клиента

Пользовательский путь:

1. Владелец создает приглашение: `POST /admin/invites` в control plane или CLI-обертка. Получает ссылку `https://join.tarassov.me/i/<inviteCode>`. Код одноразовый, живет 24 часа.
2. Клиент открывает ссылку. Control plane создает запись `accounts` со статусом `onboarding`, генерирует `accountId`, токены, ключ шифрования, создает Secret, StatefulSet и Service. IngressRoute пока не создается.
3. Страница показывает «запускаем…», пока воркер не ответит на `/v1/health` (ориентир десятки секунд, зависит от pull образа).
4. Control plane от имени админского токена вызывает `POST /v1/auth/qr`, страница опрашивает control plane, тот читает `/v1/auth/state` и отдает `qr_link`. Страница рисует QR и подпись «Telegram → Настройки → Устройства → Подключить устройство». TDLib сам обновляет ссылку, страница перерисовывает QR.
5. Если у аккаунта 2FA, состояние переходит в `wait_password`, страница просит пароль, control plane передает его в `/v1/auth/password`.
6. Запасной путь: кнопка «по номеру телефона» ведет в `/v1/auth/phone`, затем `/v1/auth/code`, затем при необходимости `/v1/auth/password`.
7. На `ready` гейтвей сразу пушит бинлог в S3 (фаза 0, пункт 5). Control plane вызывает `/v1/me`, пишет user id и username в `accounts` и `meta.json`.
8. Проверка дубликата: если этот Telegram user id уже есть среди аккаунтов в статусе `active`, новый воркер делает logout, ресурсы удаляются, страница сообщает «этот аккаунт уже подключен». Существующий аккаунт не трогается. Аккаунты в статусе `needs_relogin` в проверке не участвуют, для них есть отдельный путь (см. «Повторный логин»).
9. Control plane создает IngressRoute, регистрирует клиентский токен в реестре MCP, переводит статус в `active`.
10. Страница один раз показывает клиентский токен и готовые инструкции: адрес API, адрес MCP, строку для `claude mcp add`, поля для custom connector claude.ai (URL `https://mcp.tarassov.me/mcp`, заголовок `X-API-Key`). Повторно токен не показывается, только перевыпуск.

Повторный логин существующего аккаунта (после удаленного logout, AUTH_KEY_DUPLICATED, отзыва сессии в Telegram):

1. Гейтвей помечает сессию мертвой, control plane переводит аккаунт в `needs_relogin` (см. «Изменения в гейтвее», пункт 4).
2. Владелец создает приглашение, привязанное к этому `accountId`: `POST /admin/accounts/<accountId>/relogin`.
3. По ссылке идет тот же QR-поток, но на существующем воркере. `accountId`, клиентский токен, ключ шифрования и архив сохраняются, у клиента ничего перенастраивать не надо.
4. На `ready` control plane сверяет Telegram user id с записанным. Если вошли другим аккаунтом, выполняется logout, аккаунт остается в `needs_relogin`, страница сообщает об ошибке.

Самообслуживания у тенанта нет, все действия после онбординга делает владелец через admin API:

1. Перевыпуск токена: владелец вызывает `POST /admin/accounts/<accountId>/token`, получает одноразовую ссылку `join.tarassov.me/t/<code>` (24 часа), по которой тенант один раз видит новый токен. Старый токен перестает работать после перезапуска пода.
2. Удаление аккаунта по просьбе тенанта: владелец вызывает `DELETE /admin/accounts/<accountId>`.

Ограничения онбординга:

1. Сессия онбординга живет 15 минут. Не успел, ресурсы удаляются, приглашение остается действительным до истечения своих 24 часов.
2. Rate limit на `join.tarassov.me` в Traefik плюс собственный лимит control plane на попытки кода и пароля.
3. Страница онбординга не получает и не хранит ни админский токен, ни session string. Браузер общается только с control plane по cookie сессии онбординга.
4. Не больше трех одновременных онбордингов: каждый открытый инвайт сразу поднимает под. Четвертый получает «попробуйте через несколько минут».
5. Два открытия одного инвайта: первое занимает его атомарно в Postgres, второе получает «ссылка уже используется».

### Control plane (новый компонент)

Новый каталог `control-plane/` в этом репозитории, TypeScript и Node, как `mcp/` и `archiver/`. Один Deployment, одна реплика.

Обязанности:

1. Хранилище: таблица `accounts` (accountId, статус, telegram user id, username, created_at, токен-хэши, владелец-инвайтер) и `invites` в отдельной базе существующего CNPG `db/postgresql`. Секретные значения (ключ шифрования, токены в открытом виде) хранятся только в K8s Secret аккаунта, в Postgres только хэши.
2. Reconcile: раз в 30 секунд и по каждому изменению сверяет `accounts` с объектами в кластере по лейблам и приводит в соответствие: Secret, StatefulSet, Service, IngressRoute, NetworkPolicy. Ресурсы с лейблом `managed-by=control-plane` без записи в базе удаляются.
3. Онбординг: страницы и прокси пяти auth-вызовов к воркеру.
4. Реестр для MCP и архиватора: внутренний эндпоинт `GET /internal/registry`. MCP получает `sha256(клиентский токен) → {accountIds, gatewayUrl, serviceToken}`, архиватор получает `accountId → {gatewayUrl, archiverGatewayToken, archive_enabled}`. Каждый потребитель видит только свою часть, по своему сервисному токену. Защищен NetworkPolicy.
5. Admin API: инвайты, список аккаунтов со статусом и `tgw_ready`, перевыпуск токена, удаление.
6. Удаление аккаунта, по шагам: `POST /v1/auth/logout` на воркере (новый эндпоинт), ожидание остановки пода, удаление объектов S3 `telegram-sessions/<accountId>/*`, вызов purge в архиваторе, удаление Secret и записи в базе. Шаг с S3 строго после остановки пода, иначе финальный push на shutdown вернет бинлог.
7. RBAC: ServiceAccount с Role в `tgw` на Secret, StatefulSet, Service, NetworkPolicy, IngressRoute, Middleware. Ничего за пределами namespace.

Почему не CRD и оператор: control plane все равно нужен для онбординга и реестра токенов, второй источник истины в виде CRD добавил бы синхронизацию без выигрыша. Это решение исполнителя-проектировщика, а не владельца.

### MCP

1. Один Deployment, один Service, хост `mcp.tarassov.me`. Per-account деплойменты удаляются после миграции.
2. Токен из `Authorization: Bearer` или `X-API-Key`, как сейчас. Резолвится через реестр control plane с кэшем на 30 секунд. Неизвестный токен 401.
3. Рукопожатие `initialize`, `ping`, `tools/list` без токена пропускается как сейчас: `tools/list` одинаков у всех.
4. Аккаунт передается в обработчики через `req.auth` и `extra.authInfo` SDK, не через модульные константы. `api()` и скачивание файлов принимают контекст аккаунта.
5. Параметр `account` у всех инструментов. Необязателен и игнорируется, если у токена ровно один аккаунт. Обязателен, если больше одного. Новый инструмент `telegram_list_accounts`.
6. Пишущие инструменты (`send_message`, `edit_message`, `delete_messages`, `forward_messages`, `react`, `mark_read`) при наборе больше одного аккаунта без `account` возвращают ошибку, дефолта нет. В ответе всегда `account` и `from`.
7. `mcp-session-id` привязывается к хэшу токена первого авторизованного запроса. Запрос с другим токеном в той же сессии получает 404, клиент по спецификации обязан начать новую сессию. На неизвестный session id отвечать 404, а не 400, как сейчас.
8. `telegram_search_history` всегда передает в архиватор `session_id` аккаунта из контекста. Модели этот параметр не доступен.
9. Проверка `Origin` включается через опции SDK (`allowedOrigins`), спецификация транспорта требует ее.

### Архиватор

Минимум под новую модель, без расширения функциональности:

1. Наружу не выставляется. Ingress `tgw-archive.tarassov.me` удаляется.
2. `/search` требует `session_id`, без него 400. Доступ по сервисному токену MCP.
3. `/backfill` и `/stats` только с отдельным admin-токеном архиватора. `/stats` для admin-токена без изменений.
4. Новый `DELETE /accounts/<sessionId>` под admin-токеном: удаляет строки в `messages`, `chats`, `seq_state` и медиа по префиксу `media/<sessionId>/` в S3.
5. Кадры из Kafka с `session_id`, которого нет среди аккаунтов с `archive_enabled`, отбрасываются. Список берется из реестра control plane.
6. Скачивание медиа и backfill идут с токеном архиватора конкретного аккаунта из реестра, а не с общим `ARCHIVER_GATEWAY_TOKEN`. Общий токен и шаблон адреса гейтвея удаляются.
7. `ARCHIVER_S3_PUBLIC_BASE` остается пустым (так в проде на 2026-10-18), `media_url` имеет вид `s3://…` и наружу как HTTP-ссылка не отдается. Бакет `tgw-s3-bucket` не должен быть публичным на чтение, проверить политику MinIO в фазе 0.
8. Индекс `(session_id, date DESC)` в Postgres.

Не делается сейчас: RLS в Postgres, партиционирование, подписанные медиа-ссылки, масштабирование больше одной реплики.

### Изменения в гейтвее

Все небольшие, архитектура процесса не меняется.

1. Push бинлога в S3 по первому `Ready` (фаза 0).
2. `TGW_SESSION_EXPORT_ENABLED` (по умолчанию `true` ради совместимости). При `false` маршрут `GET /v1/auth/session/export` не регистрируется.
3. `POST /v1/auth/logout`: `td_api::logOut`, ожидание `Closed`, после этого не пушить бинлог в S3 при shutdown и выйти с кодом 0. Admin-скоуп.
4. После удаленного logout или AUTH_KEY_DUPLICATED процесс не уходит в петлю рестартов на мертвом бинлоге: при старте TDLib в `LoggingOut`/`Closed` сразу после восстановления из S3 гейтвей помечает сессию мертвой (`meta.json`, поле `revoked_at`), не пушит бинлог и отвечает `/v1/ready` 503 без выхода. Control plane видит состояние и показывает аккаунт как требующий повторного логина. Это возвращает поведение к решению C11 из DECISIONS.md.
5. Кэш идемпотентности, лимитер auth-попыток и трекер отправки остаются процессными. При модели «один процесс на аккаунт» они уже изолированы.

## Почему не один процесс на всех

Рассматривался вариант, где гейтвей держит много TDLib-клиентов через `td::ClientManager`, как это делают telegram-bot-api и обследованные WhatsApp-шлюзы. Отклонен:

1. Объем: параметризовать конфиг, TokenStore, bridge dispatch и IUpdateSink, около 34 хендлеров, WS-реестр, S3-синк и shutdown на N сессий, вебхуки, метрики, кэш идемпотентности, лимитер, трекер отправки.
2. Изоляция: в сценарии с чужими пользователями любая ошибка скоупинга в общем адресном пространстве дает доступ к чужому аккаунту.
3. Blast radius: один рестарт или OOM рвет все сессии, удаленный logout одного аккаунта сейчас гасит процесс.
4. Память: в issue tdlib/td #2807 и #3671 native-память многоклиентного процесса растет и возвращается только при закрытии клиента. Отдельный под делает перезапуск одного аккаунта дешевым.

## Миграция существующих аккаунтов

1. Фаза 0.
2. Control plane развернут, записи для `1000000001` и `1000000002` созданы импортом со статусом `active` и текущими `DATABASE_ENCRYPTION_KEY`.
3. Для каждого аккаунта: остановить старый Deployment из чарта `tgw` (graceful push в S3), дождаться завершения пода, только потом control plane создает StatefulSet. Одновременно двух подов на аккаунт не бывает.
4. Выпуск новых клиентских токенов, перенастройка клиентов владельца (коннекторы claude.ai, Claude Code, скрипты) на `tg.tarassov.me` и `mcp.tarassov.me`.
5. Старые хосты `tg-<id>`, `mcp-<id>`, `tgw-archive` и per-account MCP удаляются после подтверждения владельцем, что клиенты переехали.
6. Чарт `telegram-rest-gateway` перестает рендерить аккаунты (список `accounts` пустой по умолчанию) и остается для общей ConfigMap и общего Secret. Чарт tools получает control plane и одиночный MCP.

## Проверка

Обязательные тесты и проверки до объявления готовности (порядок удаления: scale StatefulSet до 0, дождаться завершения пода, потом S3; иначе StatefulSet поднимет под после logout заново):

1. Изоляция маршрутизации: токен аккаунта А с подменой префикса на Б получает 401 от пода Б. Токен без префикса и с неизвестным префиксом получает 404. Пути `/V1/Auth/session/export`, `/v1/AUTH/qr`, `/ui`, `/metrics`, `/v1/webhooks` на `tg.tarassov.me` в любом регистре не доходят до пода.
2. WebSocket через `tg.tarassov.me` с токеном в `Sec-WebSocket-Protocol` получает hello-кадр со своим `session_id`.
3. Загрузка файла 60 MiB и скачивание с `Range` через общий хост.
4. MCP: токен А не видит чатов Б ни через один инструмент. Поиск по архиву с токеном А не возвращает строк Б. Сессия, открытая токеном А, не принимает запрос с токеном Б.
5. Онбординг на тестовом аккаунте Telegram через QR и через телефон с 2FA. Убить под через 1 секунду после `ready` и убедиться, что бинлог в S3 и повторный старт авторизован.
6. Дубликат: повторный онбординг того же Telegram-аккаунта не трогает существующий и не порождает второго живого процесса.
7. Удаление: после `DELETE` аккаунта в S3 нет объектов под `telegram-sessions/<accountId>/`, в архиве нет строк, в кластере нет ресурсов с этим лейблом, в Telegram сессия закрыта.
8. Потеря ноды (симуляция `kubectl cordon` плюс остановка kubelet на тестовом стенде или чтение поведения StatefulSet): замещающий под не стартует, пока старый не удален.

2. Фреймворк HTTP и шаблонизатор страниц control plane, клиент K8s API, миграции Postgres.
3. Формат и верстка страниц онбординга, рендер QR (библиотека на клиенте или SVG с сервера).
4. Детали reconcile: информеры или опрос, порядок создания объектов.
5. Разбивка на PR и порядок, кроме того, что фаза 0 идет первой, а миграция существующих аккаунтов последней.

## Решения, принятые без владельца

Владелец сказал: свои и чужие аккаунты, токен определяет аккаунт, архиватор переделать под новую модель, если есть возможность, онбординг легкий, через QR или аналог. Все ниже мои решения, их можно оспорить:

1. Воркер на аккаунт, а не многоклиентный процесс.
2. Маршрутизация в Traefik по префиксу токена вместо своего роутера.
3. Slug как `accountId` для новых аккаунтов, существующие сохраняют числовой id.
4. Онбординг только по приглашению.
5. Один клиентский токен на API и MCP.
6. Владельческий MCP-токен на несколько аккаунтов с параметром `account`.
7. Control plane с Postgres как источником истины вместо CRD и оператора.
8. StatefulSet вместо Deployment.
9. Свой `DATABASE_ENCRYPTION_KEY` на каждый новый аккаунт, запрет session export для тенантов.
10. Вебхуки для тенантов вне этой итерации.
11. Архиватор только внутренний.
12. Повторный логин через приглашение, привязанное к существующему `accountId`, с сохранением токена.
13. Самообслуживания у тенанта нет, перевыпуск и удаление через владельца.
14. Session export выключен везде, включая аккаунты владельца, включается владельцем вручную.
15. Сертификат на три фиксированных хоста вместо wildcard.
16. Ориентир до 50 аккаунтов и не больше трех одновременных онбордингов.
17. Архив для тенантов выключен по умолчанию (`archive_enabled=false`), для аккаунтов владельца включен. Страница онбординга согласие не спрашивает: архив тенанта включает только владелец через admin API. Владелец на вопрос не ответил и сказал продолжать, поэтому взят дефолт.
    Изменено владельцем 2026-10-19: архив включен у всех аккаунтов, и у новых по умолчанию (`archive_enabled=true`).
