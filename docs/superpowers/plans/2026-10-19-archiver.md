# Архиватор под новую модель. План реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** архиватор берет адрес гейтвея и токен каждого аккаунта из реестра control plane, хранит только аккаунты с `archive_enabled`, отдает поиск строго в срезе аккаунта и умеет удалить архив аккаунта.

**Architecture:** клиент реестра (`GET /internal/registry` с `CP_REGISTRY_ARCHIVER_TOKEN`, кэш 30 с) дает `accountId -> {gatewayUrl, archiverGatewayToken, archive_enabled}`. Медиа и backfill ходят в гейтвей по этой записи. Общий `ARCHIVER_GATEWAY_TOKEN` и шаблон адреса удаляются. Админские операции (`/stats`, `/backfill`, повтор медиа, удаление аккаунта) требуют отдельный `ARCHIVER_ADMIN_TOKEN`, а `/search` остается на токене MCP.

**Tech Stack:** TypeScript, Node 22, `pg`, `kafkajs`, `@aws-sdk/client-s3`, тесты `node:test` через `tsx` (в архиваторе тестов пока нет, Task 1 их заводит).

**Spec:** `docs/superpowers/specs/2026-10-18-multi-account-single-endpoint-design.md`, раздел «Архиватор», пункты 1–8, и пункт 6 «Control plane» (удаление аккаунта вызывает purge).

## Порядок

Задачи 1 и 2 выкатываются сразу после готовности (Task 5, шаг 1): сейчас каждая загрузка медиа получает 401 и помечается `permanent fail`, а `file_id` живет только до перезапуска воркера.

## Global Constraints

1. Реестр: `ARCHIVER_REGISTRY_URL` + `ARCHIVER_REGISTRY_TOKEN`, кэш 30 с, при недоступном реестре последний снимок до 5 минут.
2. 401 и 403 от гейтвея больше не permanent: это неверный или устаревший токен, задача уходит в повтор с бэкоффом (как сетевые ошибки). 404 остается permanent.
3. `/search` без `session_id` дает 400.
4. `/stats`, `/backfill`, `POST /media/retry`, `DELETE /accounts/:sessionId` только с `ARCHIVER_ADMIN_TOKEN`. Токен MCP на них дает 403.
5. Кадр Kafka с `session_id`, которого нет в реестре или у которого `archive_enabled=false`, отбрасывается до записи в базу. Если реестр ни разу не загрузился, кадры не отбрасываются, а consumer ждет (не коммитит offset), чтобы при старте без реестра не потерять архив.
6. Индекс `messages (session_id, date DESC)`.
7. Ingress архиватора наружу удаляется, `ingress.archiverHost` в чарте игнорируется.
8. В репозиторий не попадают реальные accountId и Telegram id.

## Review Focus

1. Реестр недоступен при старте пода: ни одного кадра не потеряно, consumer продолжает после появления реестра. Тест в Task 3.
2. `DELETE /accounts/:id` с `id` вида `../x` или пустым: 400, ничего не удалено. Тест в Task 4.
3. Повтор медиа после того, как воркер перезапустился и `file_id` устарел: 404 дает permanent и не зацикливается. Тест в Task 2.
4. Аккаунт выключил архив: новые кадры не пишутся, уже записанное остается до явного purge. Тест в Task 3.
5. Токен MCP на админских путях: 403, а не 401 (клиент MCP не должен решить, что ключ неверный для поиска). Тест в Task 4.
