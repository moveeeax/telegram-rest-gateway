## 1. Назначение и область применения

Сервис оборачивает пользовательский Telegram-клиент (на базе TDLib) в HTTP-интерфейс, чтобы внешние приложения могли отправлять/читать сообщения, управлять чатами и получать обновления по стандартным веб-протоколам, не встраивая TDLib напрямую.

Ключевое отличие от официального Bot API: сервис работает под **user-аккаунтом** (логин по номеру телефона), а не под bot-токеном. Это даёт полный доступ к возможностям обычного клиента, но накладывает ограничения по ToS Telegram (см. раздел 13).

### 1.1. Что решает сервис
- Даёт языконезависимый доступ к аккаунту (любой клиент, умеющий HTTP).
- Скрывает асинхронную природу TDLib за понятной моделью «запрос → ответ».
- Управляет жизненным циклом сессии и авторизацией.
- Доставляет входящие обновления (новые сообщения и события) наружу через WebSocket.

### 1.2. Явно вне области MVP
- Не является заменой Bot API и не эмулирует его схему.
- Не хранит расшифрованное содержимое переписки дольше, чем нужно для обработки запроса.
- Не логирует тела сообщений и медиа-контент (**решение #8**).
- Multi-account, вебхуки, звонки, истории (stories) — вне первой версии.

## 2. Термины

- **TDLib** — официальная кросс-платформенная библиотека Telegram для построения клиентов. **[Факт: github.com/tdlib/td — "Cross-platform library for building Telegram clients"]**
- **Drogon** — асинхронный C++ HTTP-фреймворк. **[Факт: drogon README]**
- **`td::ClientManager`** — нативный C++-класс TDLib, управляющий одним или несколькими клиентскими экземплярами; предоставляет `create_client_id()`, `send()`, `receive()`. **[Факт: example/cpp/td_example.cpp]**
- **`client_id`** — идентификатор отдельной авторизованной сессии внутри процесса (тип `std::int32_t`).
- **`request_id`** — числовой идентификатор запроса (тип `std::uint64_t`), передаётся в `send()` и возвращается в ответе для сопоставления. `request_id == 0` в ответе означает **апдейт** (не привязан к запросу). **[Факт: td_example.cpp]**
- **API-клиент** — внешнее приложение, обращающееся к нашему сервису по HTTP/WS.

## 3. Обоснование стека

### 3.1. TDLib — нативный C++-интерфейс

TDLib берёт на себя тяжёлую часть: **[Факт: tdlib README]** «TDLib берёт на себя все детали сетевой реализации, шифрование и локальное хранение данных». Нам не нужно реализовывать MTProto, шифрование, реконнекты и локальную БД сессии — только транслировать HTTP ↔ вызовы TDLib.

**[Решение #2]** Используем **нативный C++-интерфейс** (`td::ClientManager` + типизированные объекты `td_api::*`), а не JSON-интерфейс. Обоснование:
- Мы и так пишем на C++ — типизированные объекты дают проверку на этапе компиляции и избавляют от ручной сериализации/парсинга JSON на «горячем» пути.
- Нет накладных расходов на JSON-сериализацию каждого запроса/ответа внутри процесса.
- Официальный пример **[Факт: example/cpp/td_example.cpp]** демонстрирует ровно этот путь: авторизацию, обработку входящих, получение чатов и отправку текста через `td::ClientManager`.

Компромисс, принятый осознанно: жёсткая привязка к версии TDLib (при обновлении нужно пересобрать против нового `td_api.h`) и больше кода-обвязки для маппинга типов. Это учтено в разделе 5.

Требования сборки TDLib: **[Факт: tdlib README]** компилятор с поддержкой **C++17** (Clang 5.0+, GCC 7.0+, MSVC 19.1+). Мы поднимаем планку до **C++20** ради корутин Drogon. Рантайм-зависимости: **[Факт: tdlib-delphi README]** TDLib требует **OpenSSL и ZLib**, поставляются вместе с библиотекой.

### 3.2. Drogon — почему подходит
- **[Факт: drogon README]** Полностью асинхронная модель, неблокирующий I/O на epoll (kqueue на macOS/FreeBSD).
- **[Факт: LinuxLinks/drogon]** Поддержка WebSocket (сервер и клиент) и JSON-запросов/ответов, «очень дружелюбно к разработке RESTful API».
- **[Факт: drogon wiki ENG-16/17]** Нативные C++20-корутины (`Task<HttpResponsePtr>`, `co_await`), позволяющие писать асинхронный код в линейном стиле.
- **[Факт: Grokipedia/Drogon]** Поддержка корутин добавлена начиная с версии 1.4.

**Критично для архитектуры:** **[Факт: drogon wiki ENG-17]** «Вызов корутин из WebSocket-контроллеров пока не поддерживается». Значит, канал доставки апдейтов (WebSocket) реализуем на колбэках/очередях, а не на корутинах. Учтено в разделе 6.3.

## 4. Общая архитектура

Сервис — единый процесс с несколькими логическими подсистемами и строгим разделением потоков.

```
                ┌──────────────────────────────────────────────────────────┐
                │                     Процесс сервиса                        │
                │                                                            │
  API-клиент ──HTTP──▶ ┌───────────────┐        ┌────────────────────────┐  │
  API-клиент ──WS────▶ │  Drogon        │        │  TDLib Manager          │  │
  API-клиент ──HTTP──▶ │  (event loops, │        │  (dedicated thread)     │  │
                │      │  контроллеры)  │        │                         │  │
                │      │                │        │  ┌──────────────────┐   │  │
                │      │  REST handlers │◀──────▶│  │ Correlation map  │   │  │
                │      │  WS handlers   │ запрос │  │ request_id→promise│  │  │
                │      └───────┬────────┘ /ответ │  └──────────────────┘   │  │
                │              │                 │  ClientManager::        │  │
                │      ┌───────▼────────┐        │    send / receive       │  │
                │      │ Update Router  │◀───────│  ┌──────────────────┐   │  │
                │      │ (fan-out to WS)│ апдейты│  │ client_id (сессия)│──┼──┼──▶ Telegram
                │      └────────────────┘        │  └──────────────────┘   │  │    servers
                │                                └────────────────────────┘  │
                │      ┌────────────────────────────────────────────────┐    │
                │      │ Session Store (session-каталог TDLib + метаданные)   │
                │      └────────────────────────────────────────────────┘    │
                └──────────────────────────────────────────────────────────┘
```

### Подсистемы
1. **HTTP/WS слой (Drogon)** — принимает запросы, валидирует, аутентифицирует API-клиента, формирует типизированный запрос к TDLib, ждёт ответ, сериализует результат в JSON.
2. **TDLib Manager** — владеет `td::ClientManager`, единолично вызывает `receive()`, ведёт таблицу корреляции `request_id → promise`, маршрутизирует апдейты.
3. **Update Router** — рассылает входящие апдейты подписчикам (WebSocket-соединениям).
4. **Session Store** — каталог session-файлов TDLib (пишет сама TDLib, шифрованный) + наши метаданные о сессии.

## 5. Ядро архитектуры: мост «async TDLib → request/response HTTP»

Это самая содержательная часть. Всё остальное — обвязка вокруг неё.

### 5.1. Проблема
REST по природе синхронен на уровне одного запроса: клиент ждёт ответ. TDLib же — поток: **[Факт: tdlib getting-started]** «Основной API полностью асинхронный: приложение отправляет запрос и асинхронно получает ответ, когда он готов». Ответы и апдейты приходят вперемешку в общем потоке `receive()`.

### 5.2. Механизм корреляции (нативный интерфейс)

Опора на штатное средство нативного API: у `td::ClientManager::send(client_id, request_id, function)` есть числовой **`request_id`**; ответ приходит в структуре `td::ClientManager::Response{ client_id, request_id, object }` с тем же `request_id`. **[Факт: td_example.cpp]** Если `request_id == 0`, объект — это **апдейт** (не привязан к запросу). `client_id` различает сессии (в MVP — одна).

**[Решение]** Алгоритм:
1. HTTP-хендлер генерирует уникальный монотонный `request_id` (atomic-счётчик `std::uint64_t`, начиная с 1; 0 зарезервирован под апдейты).
2. Кладёт в **таблицу корреляции** запись `request_id → std::promise/awaitable`, привязанную к текущему HTTP-запросу, с TTL.
3. Вызывает `client_manager.send(client_id, request_id, std::move(function))`, где `function` — типизированный `td_api::object_ptr<td_api::Function>`.
4. Приостанавливает HTTP-обработку через корутину Drogon `co_await` на кастомном awaitable.
5. **Выделенный поток-приёмник** в цикле зовёт `client_manager.receive(timeout)`; для каждого `Response`:
   - `request_id != 0` и найден в таблице → это **ответ**: «будим» соответствующий HTTP-запрос через `EventLoop::queueInLoop`, отдаём результат, удаляем запись;
   - `request_id == 0` → это **апдейт**: передаём в Update Router.
   - `request_id != 0`, но записи нет (истёк TTL) → логируем и отбрасываем.

### 5.3. Требование к потоку-приёмнику

**[Факт: td_example.cpp / getting-started]** `receive()` желательно вызывать из одного выделенного потока; все апдейты и ответы применяются в порядке получения для консистентности.

**[Решение]**
- Ровно **один выделенный поток** на весь процесс вызывает `receive()`.
- Этот поток **не выполняет тяжёлую работу**: только диспетчеризует (находит promise / маршрутизирует апдейт) и сразу возвращается к `receive()`, чтобы не создавать backlog. Тяжёлую обработку (маппинг в DTO, сериализация) выносим в event-loop'ы Drogon.
- Мост между потоком TDLib и потоками Drogon — через `EventLoop::queueInLoop(...)`. **[Факт: Drogon threading blog]** «Submitting task на loop полностью lock-free и не вызывает гонок при любых обстоятельствах».
- Таблица корреляции защищена мьютексом (доступ: HTTP-потоки на запись записи, поток-приёмник на чтение/удаление); контеншен низкий, т.к. критические секции короткие.

### 5.4. Корутины Drogon как интерфейс к мосту

**[Решение]** REST-хендлеры пишем как корутины (`Task<HttpResponsePtr>`), а `co_await` — на нашем awaitable (`TdAwaitable`), который резолвится из потока TDLib через `queueInLoop`. Линейный, читаемый код без callback hell — ровно то, ради чего **[Факт: drogon wiki]** «код выглядит синхронным, но на деле асинхронный».

Эскиз API моста:
```cpp
// co_await возвращает td_api::object_ptr<td_api::Object> (ответ или td_api::error)
td::Task<td_api::object_ptr<td_api::Object>>
TdBridge::invoke(std::int32_t client_id, td_api::object_ptr<td_api::Function> fn);
```

### 5.5. Таймауты и «висящие» запросы

**[Решение]** Каждой записи корреляции — TTL (по умолчанию 30 с, конфигурируемо). Если ответ не пришёл за TTL, HTTP-запрос завершается ошибкой `504 REQUEST_TIMEOUT`, запись удаляется фоновым «сборщиком» (проверка раз в 1 с). Нужно, потому что не на каждый `send` гарантированно приходит ответ (часть — fire-and-forget). Список fire-and-forget методов фиксируется по `td_api.tl` и не помещается в таблицу корреляции вовсе.

## 6. Сессия, авторизация и апдейты

### 6.1. Модель сессии (single-account)

**[Решение #1]** В MVP процесс держит **ровно один** `client_id`, созданный через `client_manager.create_client_id()`. Первый запрос к клиенту (любой, напр. `getOption`) инициирует поток `updateAuthorizationState`. **[Факт: td_example.cpp]** новый экземпляр создаётся `create_client_id()`, объекты помечаются `client_id`.

API спроектирован с параметром `session_id` (см. раздел 8) на будущее, но в MVP значение фиксировано (`default`), и обращения к чужим сессиям невозможны.

### 6.2. Хранение сессии

TDLib сама хранит ключи авторизации и состояние в локальной директории (`database_directory` / `files_directory` в `setTdlibParameters`).

**[Решение #8]**
- Отдельная директория сессии, права **`0700`**.
- Включено штатное **шифрование БД TDLib**: `setTdlibParameters.database_encryption_key` (ключ — из конфига/env, не в коде).
- В Docker — на именованном volume; бэкап и права доступа критичны (в каталоге — фактический доступ к аккаунту).

### 6.3. Доставка апдейтов наружу (WebSocket)

**[Решение #6]** Единственный канал MVP — **WebSocket**: API-клиент открывает `WS /v1/updates`, аутентифицируется, подписывается на апдейты. Update Router делает fan-out.

**Ограничение фреймворка:** **[Факт: drogon wiki ENG-17]** «вызов корутин из WebSocket-контроллеров пока не поддерживается». Поэтому WS-контроллеры реализуем на **колбэках**: поток TDLib кладёт апдейт в очередь роутера, роутер через `queueInLoop` пушит в активные WS-соединения (each connection на своём event loop).

**[Решение]** Модель подписки MVP: клиент получает все апдейты своей сессии (фильтрация по типам — опционально, вне MVP). При переполнении исходящего буфера соединения — политика back-pressure: медленный клиент отключается с кодом ошибки (защита от неограниченного роста памяти).

Вебхуки — **вне MVP** (решение #6), но раздел API оставляет место для расширения.

## 7. Авторизация Telegram-аккаунта

### 7.1. Природа проблемы
Логин в TDLib — **конечный автомат**, а не один вызов. **[Факт: tdlib getting-started]** «Авторизация управляется через обновления `updateAuthorizationState`; первое состояние всегда `authorizationStateWaitTdlibParameters`, и приложение должно передать параметры через `setTdlibParameters`». Далее — ожидание номера, кода из СМС/приложения, при 2FA — пароля. Интерактивный ввод плохо ложится на один HTTP-запрос.

### 7.2. Поток авторизации (REST)
**[Решение]** Состояния автомата → эндпоинты:

1. `POST /v1/auth/session` — создать сессию (`create_client_id`, отправить `setTdlibParameters` с api_id/api_hash и `database_encryption_key`). Возвращает `session_id` и текущее `authorization_state`.
2. `POST /v1/auth/{session_id}/phone` — отправить номер (`setAuthenticationPhoneNumber`).
3. `POST /v1/auth/{session_id}/code` — отправить код (`checkAuthenticationCode`).
4. `POST /v1/auth/{session_id}/password` — 2FA-пароль (`checkAuthenticationPassword`), если требуется.
5. `GET  /v1/auth/{session_id}/state` — текущее `authorization_state` (для поллинга UI).

После `authorizationStateReady` TDLib сохраняет сессию на диск; повторный логин при рестарте не требуется, пока живы session-файлы.

**[Решение]** api_id/api_hash получаются заказчиком на my.telegram.org и передаются сервису через конфиг/env, **не** через публичный API. Их утечка = компрометация приложения.

## 8. Спецификация API (v1)

Все ответы — JSON. Ошибки — единый формат (раздел 9). Версионирование — префикс `/v1`.

### 8.1. Аутентификация API-клиента
**[Решение #5]** Каждый запрос (кроме `/v1/health`) требует статический API-токен: `Authorization: Bearer <token>`. Токен(ы) — из конфига. Реализуется как pre-handling advice / filter Drogon. Защищает сам сервис: иначе любой, кто достучится до порта, получит доступ к аккаунту.

Для `WS /v1/updates` токен передаётся в заголовке при рукопожатии (или query-параметром для клиентов, не умеющих заголовки на WS — с пометкой о рисках в логах прокси).

### 8.2. Эндпоинты MVP

| Метод | Путь | td_api (примерно) | Назначение |
|---|---|---|---|
| `GET` | `/v1/health` | — | Живость сервиса (без auth) |
| `POST` | `/v1/auth/session` | `setTdlibParameters` | Создать сессию |
| `POST` | `/v1/auth/{sid}/phone` | `setAuthenticationPhoneNumber` | Номер телефона |
| `POST` | `/v1/auth/{sid}/code` | `checkAuthenticationCode` | Код подтверждения |
| `POST` | `/v1/auth/{sid}/password` | `checkAuthenticationPassword` | 2FA-пароль |
| `GET` | `/v1/auth/{sid}/state` | (из `updateAuthorizationState`) | Состояние авторизации |
| `GET` | `/v1/me` | `getMe` | Инфо о текущем аккаунте |
| `GET` | `/v1/chats?limit=&offset=` | `getChats` | Список чатов |
| `GET` | `/v1/chats/{chat_id}/messages?limit=&from_id=` | `getChatHistory` | История сообщений |
| `POST` | `/v1/chats/{chat_id}/messages` | `sendMessage` | Отправить текст |
| `POST` | `/v1/chats/{chat_id}/messages/{id}/read` | `viewMessages` | Отметить прочитанным |
| `POST` | `/v1/files/upload` | `uploadFile` / `sendMessage` | Загрузить файл |
| `GET` | `/v1/files/{file_id}` | `downloadFile` / `getFile` | Скачать/статус файла (стриминг) |
| `WS` | `/v1/updates` | (fan-out апдейтов) | Поток апдейтов |

**[Решение]** Тела запросов и структуры ответов — **тонкая проекция (DTO)** объектов `td_api`, а не полное копирование: наружу отдаём только нужные поля, внутренние скрываем. Полная схема — `td_api.tl` / автогенерируемая HTML-документация. **[Факт: tdlib README]** ссылается на неё как на источник всех методов и классов.

### 8.3. Загрузка/скачивание файлов (стриминг)
Файлы в TDLib асинхронны: у файла есть идентификатор, он может быть локально или на сервере, качается/заливается отдельно. **[Факт: tdlib getting-started]** «Каждый файл имеет идентификатор и может быть доступен локально или удалённо».

**[Решение #7]** Скачивание — **стриминг через сервис**:
- `GET /v1/files/{file_id}` инициирует `downloadFile` (если не докачан), возвращает `202 Accepted` со статусом и прогрессом; при полной загрузке — стримит байты через Drogon (`HttpResponse` с телом-стримом / chunked), читая локальный путь из `td_api::file.local.path`.
- Файловая система наружу не публикуется; временных публичных URL нет.
- Для больших файлов — потоковая отдача чанками, без загрузки целиком в память.
- Загрузка (`upload`): `multipart/form-data` → временный файл → `sendMessage` с `inputFileLocal`.

## 9. Обработка ошибок

**[Решение]** Единый конверт ошибки:
```json
{ "ok": false, "error": { "code": "TELEGRAM_ERROR", "message": "...", "tdlib_code": 400, "tdlib_message": "CHAT_NOT_FOUND" } }
```
Классы ошибок:
- **Ошибки TDLib/Telegram** — объект `td_api::error` (пробрасываем `code`/`message` в `tdlib_code`/`tdlib_message`).
- **Ошибки авторизации** — неверный код, требуется пароль и т.п.
- **Ошибки сервиса** — таймаут корреляции (`504`), сессия не найдена (`404`), невалидный ввод (`400`).
- **Ошибки аутентификации API-клиента** — `401` (нет/битый токен) / `403`.

HTTP-статусы маппятся по классу ошибки; тело всегда в конверте выше.

## 10. Нефункциональные требования

- **Потокобезопасность:** ровно один поток на `receive()`; всё межпоточное — через `queueInLoop` / короткие критические секции. **[Факт: Drogon]** submitting task на loop — lock-free.
- **Производительность:** узкое место — не HTTP-слой (**[Факт: drogon.org]** Drogon держит 150K+ req/s), а диспетчеризация и лимиты Telegram (flood-wait). Профиль — I/O-bound. Нативный интерфейс убирает JSON-сериализацию с горячего пути.
- **Наблюдаемость:** структурные логи (correlation id = `request_id`), метрики (состояние авторизации, глубина очереди апдейтов, число WS-подписчиков, латентность мост-ответа, таймауты), эндпоинты health/readiness. **Логи не содержат тел сообщений и контента** (решение #8).
- **Конфигурация:** api_id/api_hash, `database_encryption_key`, Bearer-токены API, число потоков Drogon, путь session-директории, TTL корреляции, лимиты WS-буфера — через конфиг/env.
- **Устойчивость:** корректная обработка `authorizationStateClosed` (флаг закрытия, освобождение ресурсов); авто-переподключение — на стороне TDLib. При `authorizationStateClosing/Closed` — сервис отвечает `503` на запросы к сессии.
- **Секреты:** api_hash, `database_encryption_key`, Bearer-токены — только из env/secret manager; никогда в код, логи, образ.

## 11. Сборка и деплой

- **Язык/стандарт:** **C++20** (требование — корутины Drogon; TDLib требует минимум C++17 **[Факт: tdlib README]**).
- **Зависимости рантайма:** TDLib + **OpenSSL + ZLib** (**[Факт: tdlib-delphi]**). Символы TDLib линкуются с системным OpenSSL (известный класс проблем при неправильной линковке — следить в CI).
- **Сборка:** CMake + presets. TDLib собирается штатным CMake-путём (**[Факт: tdlib README]**). Наш таргет линкуется против `Td::TdStatic`/`Td::TdShared` (динамическая линковка — решение #4).
- **[Решение #4]** Артефакт — **multi-arch Docker-образ** (`linux/amd64` + `linux/arm64` через `buildx`), multi-stage:
  - стадия сборки: собирает TDLib и Drogon, затем наш бинарь;
  - финальная стадия: тонкий образ (distroless/slim) с бинарём и `.so` (TDLib, OpenSSL, ZLib).
  - Session-директория — на volume; `database_encryption_key` и токены — через env/secret.
- **CI (GitLab):** сборка обеих архитектур, unit-тесты моста, линт (`clang-format`, `clang-tidy`), сборка образа. Кэширование слоя сборки TDLib (долгий шаг).

## 13. Риски и ограничения (согласовано)

- **ToS Telegram.** Автоматизация под пользовательским аккаунтом (userbot) — зона риска блокировки. Документированное предупреждение для любых MTProto-клиентов, не специфично для нас. Заказчик подтверждает допустимость и характер нагрузки; соблюдаем flood-wait.
- **Хранение доступа к аккаунту.** Session-директория фактически содержит доступ к аккаунту. Митигация (решение #8): шифрование БД TDLib, права `0700`, ключ вне образа, аудит доступа к volume.
- **Привязка к версии TDLib.** Нативный интерфейс требует пересборки против нового `td_api.h` при апгрейде TDLib. Митигация: зафиксированная версия TDLib в сборке, обновление — через отдельную `feature/*` с прогоном тестов моста.
- **Ограничение корутин в WS-контроллерах Drogon** (**[Факт]**) — известное ограничение фреймворка, обойдено колбэками (раздел 6.3).
- **Отсутствие готового эталона.** Нет общепризнанной поддерживаемой связки «TDLib C++ + Drogon как REST» из коробки — решение проектируется как заказное. Референс: пример `td_example.cpp` и обёртки под другие языки.

## 14. Критерии приёмки MVP

1. `docker run` поднимает сервис; `GET /v1/health` → `200`.
2. Полный цикл авторизации через `/v1/auth/*` до `authorizationStateReady`; сессия переживает рестарт контейнера (volume).
3. `GET /v1/me` возвращает данные аккаунта; запрос без Bearer-токена → `401`.
4. Отправка и чтение текстового сообщения в реальный чат; история читается.
5. Upload файла и стриминг download работают на файле > 50 МБ без OOM.
6. `WS /v1/updates` доставляет `updateNewMessage` в реальном времени ≥ 2 параллельным подписчикам.
7. Таймаут корреляции даёт `504`, а не зависание; сервис остаётся живым.
8. Логи не содержат тел сообщений; session-каталог зашифрован и имеет права `0700`.
9. CI собирает `linux/amd64` и `linux/arm64`, прогоняет unit-тесты моста, линт чист.
